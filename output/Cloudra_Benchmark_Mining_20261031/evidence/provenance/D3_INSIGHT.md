# 两段可采用的解释

**Cloudra有时完成的是“自己交付内容的验证”，而不是“任务指定转化的验证”。** 以下仅使用档案实际报告的D3变体对应记录说明检查范围的区别，不用该辅助子集推断正式200次运行的总体比例。三个案例尤其清楚：guided/F4、brief/F4和brief/NU6的全图自洽都是1.0，但覆盖参考步骤的子图自洽都是0，accuracy也全为0。NU6交付了一条直接协同RC→P路径，却没有参考机理要求的两步中间体路径，覆盖0/2；F4有目标加合物，但缺形成步骤的能垒证据。这里“证据是真的”和“回答了指定的机理问题”可以同时得到不同结论：局部验证闭合，并不会自动让目标机理闭合。

**同一张交付图又承担探索笔记，会产生相反方向的问题：补充研究反而稀释目标证据的完成程度。** record/NB1的全图自洽是.675，限制到已覆盖参考步骤后是1.0；record/HI1则从.7833变成1.0。两次变化都没有补算、没有放宽证据要求，只改变哪些交付边进入平均；若只替换这一分项，对综合分的影响分别是+.0975和+.0650。这说明一个平均值混合了“目标步骤的证据是否闭合”和“额外探索是否全部收尾”两种不同状态。设计上真正值得区分的是研究主张与探索记录：主张对应哪条目标转化、由哪组证据支持；还在探索的侧支单独保留研究价值。单纯要求多做验证，可能继续把证据投入用在偏离目标的分支，也可能让扩展研究拖低已成立的目标证据。

# 来源及语义

- `docs/ADJUDICATION_METHOD.md:123-139`：selfc_gold只报告，不改官方分数；一对一匹配gold边与交付边，复用已有edge check，只平均被匹配交付边。gold有边但无覆盖=0；gold无边=1。
- `docs/scorer_fix.patch:224-289`：实际实现。`edge_scores`来自同一份report，`scores`仅按`covered_delivered`筛选，再求平均；并无新的证据验收。
- 当前仓库`cloudra/benchmark/selfconsistency.py:595-604`：all优先平均交付边；没有边时回到物种分数。因此F4不能一律描述为“完成了另一个反应的验证”，它也可能只验证了物种。
- 主表CSV行：brief/F4 7、brief/NU6 47、guided/F4 57、record/HI1 118、record/NB1 139。
- catalog CSV行：guided/F4 22、brief/F4 25、record/NB1 83、brief/NU6 117、record/HI1 153。NU6旧flex表行37给出delivered_edges=1，gold_edges_matched=0，gold_edges_unmatched=2；这几例对应分值均与最终表一致。
- 正式Graph、SC、Accuracy分项共200×3个真实值，全部进入主报告分解。`selfc_gold`是另一个辅助变体，原档案没有为6条早期回填和7条后来离线补图保存可对应的新变体值；`d3_selfc_pairs.csv`只保留已有变体记录，不作为主报告组件分母。

# 单独保留的解释边界

selfc_gold不是“完整目标机理的科学通过率”：它只平均**已经覆盖的子集**，没有匹配的其它gold边不进入分母。故NB1=1最多说明被覆盖目标步骤自洽，不能单靠它断言全部步骤齐全。无gold边的impossible题会空洞记1，本结论统计已排除impossible，避免把该约定误作证据改善。本次没有原始sandbox，因此不独立重审D3的物种匹配是否准确，也不建议直接用它替换官方分数。
