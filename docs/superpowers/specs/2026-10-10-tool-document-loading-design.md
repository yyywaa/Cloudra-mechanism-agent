# 工具说明按需加载需求与设计

日期：2026-10-10

状态：用户已确认，2026-10-10

Cloudra 保留现有 Agent 体系和工具注册表。每个 Agent 常驻一份覆盖其可用工具的简短能力目录，首次执行任务时筛选并预加载相关工具的详细说明，随后按工具名称读取更多说明。两种筛选策略共用同一套目录、文档生成、校验和加载流程。

## 已确认的需求

1. 支持两种策略：默认复用用户已配置的 LLM 做一次临时选择调用；可选使用 Jev 或国内 Reranker 做语义筛选。
2. 工具的简短能力介绍始终保留在 prompt 中，Agent 能发现初始未选中的能力。
3. 筛选结果只决定预加载哪些详细说明，不改变工具权限、计算准入或科学证据要求。
4. 临时选择调用只输出工具名称列表，完成后结束。无需增加持久 Agent、角色目录或按工具类别划分的子 Agent 系统。
5. 详细参数契约来自真实工具定义；程序根据选择结果组装说明，筛选模型不撰写或改写工具契约。

## 当前代码依据

- [tool_catalog.py](../../../cloudra/runtime_v2/tool_catalog.py)：默认 JavaScript 协议已将业务调用收进 `js_exec`，但 `javascript_instructions()` 仍通过 `tool_declarations()` 安装所有允许工具的完整输入、输出类型和描述。
- [adapters.py](../../../cloudra/runtime_v2/adapters.py)：工具协议作为会话静态前缀的一部分安装，并管理前缀恢复、来源版本和动态观察。变动时追加带来源的消息，不改写已发送的前缀。
- [js_runtime.py](../../../cloudra/runtime_v2/js_runtime.py)：JS 宿主接收允许工具的名称，真实调用继续经过当前准入与执行路径。
- [get_skill.py](../../../cloudra/tools/Skilltool/get_skill.py)：已有简短目录与完整说明按需读取的模式，可沿用其交互方式。
- [agent_runner.py](../../../cloudra/runtime_v2/agent_runner.py) 与 [turn_pipeline.py](../../../cloudra/runtime_v2/turn_pipeline.py)：当前前缀 owner 的创建和安装先于首轮任务输入追加。筛选需要使用已经准备好的真实任务输入，不能直接塞进现有无任务参数的前缀安装函数。

本期交付路径是当前默认的 JavaScript 协议。显式 `traditional` 协议继续使用其现有完整工具 schema 投影，本期不把它列入上下文减量验收，也不在筛选失败时自动切换调用协议。

## 共同的文档加载流程

### 常驻能力目录

目录对每个可用工具至少给出准确名称、简短用途、主要输入与产出概念，以及会影响选择的关键边界。简介需能区分相似工具；避免对已有长描述机械截断。

例如，`ts_prepare` 表示创建并启动一个持久 TS 路径；`ts_inspect` 表示查看权威状态、证据和缺失输入；`ts_resume` 表示带原因和版本约束修订已有路径。三者不能都缩写成“处理 TS”。

目录和详细说明沿用同一工具注册源。候选集合遵守现有 capabilities、角色、编排模式、配置开关及视觉模式过滤；具体动作的读写权限仍由执行准入检查。已隐藏的工具不会通过筛选或文档读取重新暴露。

JavaScript 协议、文档读取入口以及允许的直接控制工具保留必要的完整调用说明。其他业务工具的完整参数和返回类型按需展开。文档读取入口属于常驻基础能力，有效空选择或筛选失败均不能移除它。

### 初始文档包

程序向选定策略提供当前任务、必要的当前状态和可用工具简介。上下文只包含已经交给该 Agent 的任务及交接信息；无需发送整个父 Agent 会话或扫描工作区。

策略返回工具名称列表，例如：

```json
["ts_prepare", "ts_inspect", "ts_resume"]
```

程序通过 Pydantic 和显式集合比对校验结果。列表元素必须是当前候选集合内的准确工具名；重复名称可稳定去重，非字符串、未知名称或越权名称使本次筛选失败，禁止模糊修复或静默删除错误项。有效空列表 `[]` 表示没有详细说明需要预加载。

程序使用已选名称生成初始文档包，包含工具用途、完整输入与输出契约、必要的使用边界和最小调用示例。schema 直接来自工具的 Pydantic 模型和现有声明生成逻辑；操作示例与工具契约一同维护。

### 后续按需读取

提供一个按准确工具名称批量读取说明的入口，交互形式为 `get_tool_docs(names=[...])`。初始预加载和该入口复用同一文档生成逻辑。

返回内容标明工具名称、文档版本、完整契约和可进一步读取的参考资料。Agent 可以根据常驻目录主动加载初始未选中的工具说明。读取文档不注册新权限；调用业务工具也不以“曾加载文档”为新的权限条件。

prompt 要求 Agent 在缺少完整调用契约时先读取说明。参数合法性由原有执行校验保证，不能依赖模型自述已经阅读或理解。

## 两种筛选策略

| 策略 | 输入与选择方式 | 配置与输出 |
| --- | --- | --- |
| 现有 LLM，默认 | 临时选择调用读取任务和工具简介，只返回名称数组；无工具执行权限 | 沿用主 Agent 本次运行解析后的连接、凭据和模型配置；用户无需另配选择模型 |
| 语义筛选，可选 | 对任务与各工具简介作相关性判断；支持多个工具同时相关 | 用户选择 Jev 或已部署的国内 Reranker 服务；程序将后端结果转换为同一种名称列表 |

### Jev 后端

以当前任务为 state，对每个工具提出独立的 Noul 问题，在一个请求中批量判断其详细说明是否有助于当前任务。工具名、能力简介和必要边界必须进入问题或 state，不能只放在返回结果的字典键中。

Noul 返回各命题的成立概率。多个工具可以同时入选。Jev 的 Choice 为竞争性的单选分布，本期不将其概率直接解释为各工具独立的相关性。

### 国内 Reranker 后端

接入已部署的 Reranker 服务，为“当前任务与必要状态”和“单个工具的能力说明”逐对打分。推荐首先验证 Qwen3-Reranker-0.6B；BGE 可作为评测对照。

本期包含对这一类服务的接入与结果转换，不包含在 Cloudra 内自动下载权重、训练模型或管理推理服务。模型服务部署与选择调用分开管理，避免增加计算服务的重量依赖。

Jev 概率与 Reranker 分数使用各自的筛选规则。不能共用未经验证的阈值，也不能把归一化相关性分数直接当成校准概率。名单大小或分数边界根据代表性工具选择任务确定，并纳入该后端的验证记录。

### 兼容关系

两种策略是可切换的选择方式。语义策略下，Jev 和 Reranker 是不同后端。共同交付物都是校验后的工具名列表，后续文档组装、按需读取、权限和执行路径完全共用。

一次筛选只运行所选策略和后端，不同时启动两条选择链。默认 LLM 模式不依赖 Jev 凭据或本地 Reranker 服务。

## 触发时点与上下文管理

1. 新 Agent 首次收到实际任务，在本轮任务输入准备好后、第一次主推理请求前执行一次筛选。创建空会话时延后到任务到达，避免在同步构造函数或缺少任务原文的前缀安装函数中发起网络请求。不得使用 UI 的 `current_task` 摘要代替任务原文。
2. 自动预选择绑定会话上下文的首次任务，仅执行一次。后续任务通过常驻目录按需加载说明；本期不增加自动判断“任务明显变化”的模型或逐轮重选。新建 Agent 上下文会重新执行首次选择，普通工具轮次、计算完成唤醒、审批恢复和进程重启不重复筛选。
3. 筛选与预加载结果归属于当前 Agent 和首次任务，记录所用策略、后端、目录版本和已选工具名，供现有事件与用量链路查看。选择名单与 `AgentCapabilities.tools` 分开保存，不覆盖授权名单。
4. 常驻能力目录及基础协议保持稳定。任务相关文档作为有来源和版本的上下文内容安装，避免每轮重写静态前缀或追加相同说明。
5. 恢复会话时复用有效选择结果；读取文档时以当前契约为准。目录或文档版本发生变化时，明确标记新内容替代旧说明，不能继续按过期 schema 调用。
6. 上下文折叠后仍提供工具简介目录和文档读取入口。详细说明被折叠时可重新读取，不能把“历史加载过”视为内容仍然存在于当前上下文。

所有可能阻塞的读盘、文档生成和网络操作遵守现有异步规范。筛选期间可取消本次选择调用；它没有提交计算或修改计算进程的权限。

## 配置与失败处理

用户看到两个选择方式：“现有模型”和“语义筛选”。默认选“现有模型”；语义模式额外选择 Jev 或 Reranker，并配置对应端点、模型及必要凭据。凭据沿用项目现有的写入与脱敏规范，配置修改走 `mutate_config`。

未配置完整的语义后端时，配置校验明确拒绝启用该后端。运行时遇到网络失败、错误响应或无效工具名，记录可见的筛选失败与原因；本次不安装预加载文档包。主 Agent 仍可通过常驻目录和按需读取入口完成任务。

有效空选择和失败必须是不同状态。禁止悄悄改用另一策略、补成全量工具 schema，或把失败描述为成功筛选。此处理只影响文档预加载，不把 Agent 的科学任务或已有计算作业标记为失败。

## 验收条件

### 功能与行为

- 默认 LLM 模式无需新 API 配置，可以得到校验后的名称列表并预加载对应说明。
- Jev 与国内 Reranker 服务可分别产生选择结果，共用文档加载路径。
- 常驻目录保留当前可用工具的完整覆盖，未预加载工具可正常读取说明并调用。
- 空选择、非法名称、越权名称、格式错误和服务失败都有独立且可观测的结果。
- 文档加载不扩大权限；初始未选中的合法工具不被禁止调用。
- 会话恢复、审批恢复和后台唤醒不产生重复选择；契约更新和上下文折叠后的读取结果正确。
- 工具调用依然经过原有准入、参数校验、完整回执和科学证据检查。

### 效果验证

采用一组固定的代表性任务，对比当前全量说明方式、LLM 选择方式和语义选择方式。任务包含相似工具辨别、多工具组合、纯解释请求、初始漏选后的补充读取，以及筛选服务不可用。

记录常驻与预加载文档量、实际 prompt token、启动增加的耗时、选择调用用量、工具漏选与无关预加载、首次调用参数错误，以及任务完成后的证据完整性。选择正确性允许多种有效工具组合，不以固定调用名称序列或自然语言措辞作为唯一答案。

工程回归使用相关 runtime 场景和真实边界校验；LLM 与语义服务响应通过脚本化 provider 模拟。修复逻辑死锁或运行故障时增加场景回归。按仓库规范运行语法、ruff、相关模块测试及异步守卫，不运行本地全套测试。

## 本期边界

本期聚焦工具说明的初始筛选、按需读取和上下文减量。工具实现、科研流程与科学验收规则继续由现有模块维护。按工具类别建立子 Agent、通用插件框架、向量数据库、工具自动生成与训练模型均不属于本期需求。
