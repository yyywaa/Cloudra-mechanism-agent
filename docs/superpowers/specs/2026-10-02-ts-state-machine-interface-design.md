# TS 状态机接口与续接语义设计

日期：2026-10-02

状态：用户已于 2026-10-02 批准设计；进入实施计划阶段，尚未实施

范围：TS 工具接口、流程状态投影、输入修订与证据复用，以及 GitHub #108–#111 的相关修复

## 1. 已确认的设计语义

本规格依据本次讨论，取代旧 TS 设计中与下列决定冲突的部分：

1. TS 工具是持久状态机。Agent 选择输入、方法和补救路线，系统维护状态、执行计算、核验证据并自动接续。
2. 同一条探索路径只创建一次：`ts_prepare` 建立记录，后续调整、失败恢复、换路线和继续探索均用 `ts_resume`，保持同一个 `run_id`。
3. 正常步骤完成后由系统自动推进。输入完整且计算顺利时，一次 `ts_prepare` 可以自动跑完验证链，不要求 Agent 逐步调用 `ts_resume`。
4. Agent 必须能够直接读取状态。提供独立只读的 `ts_inspect`；事件通知与主动读取并存。
5. 参数按反应声明、构象准备、初猜搜索、TS 优化和验证分组。`xtb_path` 属于初猜搜索；扫描的方法放在扫描分支中。
6. 不默认选择科学计算方法，不在阶段之间隐式继承方法。扫描采用的半经验方法由 Agent 显式选择；这一授权不扩大为任意改变正式计算方法。
7. 删除预估时间及其准入限制。保留实际耗时与资源使用记录，不以缺少估计或预计 CPU 小时不足阻塞 TS。
8. `ts_prepare` 与 `ts_resume` 使用同一套科学输入结构。不能出现创建时允许声明、受阻后提示修改、续接接口却无法表达的字段。
9. 一次尝试失败或结束不等于整条路径不可继续。新输入可在原记录内形成新尝试，历史结果与证据保留。
10. 不新增通用工作流框架、计算队列、后台服务或科学阈值。

本文将“同一路径”定义为一条探索记录及其 `run_dir`。一个 workspace 可以容纳多个独立反应的记录；不把整个 workspace 限制成只能调用一次 prepare。输入方案修订不创建新的运行目录来规避旧失败或额度。

接口字段名、修订规则和状态返回结构是对上述语义的工程化提案，随本规格一起审阅。

## 2. 当前实现的问题

现有事实以 `cloudra/tools/Chemtool/ts_search_process.py`、`cloudra/tools/core/ts_process.py` 和 `cloudra/services/ts_pipeline_store.py` 为依据。

- `TsDeclaration` 将正式方法、扫描、xTB 溶剂、构象引导和已有 IRC 日志平铺；调用者难以辨认适用阶段。
- `TsAdjustment` 是另一份不完整的字段集合，不能修改正式方法、引擎、两端物种等；部分阻塞提示却要求修改这些字段。
- 空 `ts_resume` 能读检查点，但工具属于写操作并要求原 owner；返回内容也不包含完整声明、作业、修订历史与实际消耗。
- `legal_actions` 对候选流程返回固定列表，未按当前证据、权限和前置条件计算。
- 系统已有自动推进和持久作业绑定；“完成后再调用 resume”的旧提示与实际行为冲突。
- 部分 terminal 状态关闭了继续探索入口，迫使调用者另建流程。
- 调整主要按字段是否变化决定重跑，缺少清楚的失败依据和变更影响说明。

## 3. 工具边界

保留两个写工具，增加一个读工具，不改为通用 action 分发器。

| 工具 | 语义 | 副作用 |
|---|---|---|
| `ts_prepare(input, request_key, workspace_dir?)` | 创建路径、保存当前已知输入，然后自动推进 | 可产生构建与计算作业 |
| `ts_inspect(run_id, workspace_dir?)` | 读取当前权威快照及详细记录入口 | 不推进、不入队、不增加介入次数 |
| `ts_resume(run_id, changes, reason, request_key, expected_revision, recovery?, workspace_dir?)` | 修订输入或基于恢复证据重试，在原路径继续 | 可产生新的阶段尝试和作业 |

`request_key` 是请求幂等键，可以由宿主根据稳定的调用标识提供。相同键和相同请求返回已有处理结果；相同键与不同内容明确冲突。prepare 重试不会新建路径；已创建记录不能通过 prepare 接受新的声明，必须使用 resume。

`expected_revision` 来自 inspect 或上次工具返回，防止 Agent 根据旧状态操作。已处理请求先命中幂等记录，不因其原 revision 过期而失去可重试性。所有写入仍由现有锁和数据库事务串行化。

空 `changes` 且没有 `recovery` 的 resume 是无动作调用，返回明确错误并指向 inspect。读取不再隐藏在写接口中。重复提交无实际变化且没有恢复证据的声明返回未改变的状态，不清除失败、不重新入队、不增加介入计数。

## 4. 统一输入结构

下面是职责与字段分组约定，不是新增一套量化输入语言。具体原生参数继续复用已有工具的 Pydantic schema 与输入生成器；已支持的能力随字段迁移，不能靠改名丢失。

```text
input
  reaction
    reactant_smiles, product_smiles, charge, multiplicity
    atom_map, reaction_center
  conformers
    reactant, product
    guidance: ring_order, distance_filters
  guess
    kind: xtb_path | scan | provided
    仅包含对应分支的字段
  ts_optimization
    calculation, settings
  verification
    frequency, irc
    reactant_endpoint, product_endpoint
  execution
    cpus, memory_mb
    已有非时间类额度（若任务配置）
```

### 4.1 反应与构象准备

`reaction` 声明目标物种、完整原子对应关系和反应中心。改变目标声明也走 resume，产生修订并重新核验依赖；不能因此重置账本或让旧结论适用于新目标。

`conformers.reactant/product` 各自采用显式来源：从物种生成、已有结构文件、已有构象档案中的选定候选；产物还支持现有绕键旋转来源。每个来源只接收该来源需要的字段。涉及构象生成、预优化或约束优化时，在该来源下显式填写对应算法及计算方法。

`guidance` 只描述预组织几何条件。构象生成、候选分区和统计分析继续复用专门工具；TS 接口接收相关来源和选择，不把完整候选分析工作台继续塞进顶层 resume。已有候选引用包含档案、版本和候选身份，相关证据保持可追溯。

### 4.2 初猜搜索

`guess` 是由 `kind` 判别的联合类型：

| kind | 意义 | 分支内容 |
|---|---|---|
| `xtb_path` | 根据两端几何搜索路径候选 | 显式 xTB 方法与溶剂声明、现有路径参数 |
| `scan` | 通过声明的扫描坐标生成 TS 候选 | 显式计算方法、扫描坐标与范围、点数、冻结坐标 |
| `provided` | 接入已有 TS 初猜 | 结构引用、来源及原子身份/顺序绑定 |

不同分支的字段不能混用。切换 kind 原子性替换整个 guess 分支，旧扫描参数不会遗留到路径搜索中。移除 guess 表示当前未选择初猜路线，到需要初猜时停下，不代表跳过该证据要求。

已有扫描结果可经已有扫描解析工具生成带来源的候选，再以 `provided` 接入；无需再为各种文件发明导入动作。外部 TS 初猜只是候选，不能自带 `verified` 身份。

接入候选后按实际依赖补足证据：已具备当前步骤所需的几何与身份绑定时，不强制重新执行构象生成和初猜搜索。仍缺少的目标物种、映射或验证所需端点资料必须明确补足；来源不明的文件不能被当作已经完成的上游步骤。

本次对外首批路线限定为以上已有可接线能力，不新增搜索算法。xTB 不可用或失败时保留原因，不能静默改成另一条方法路线。已有 IDPP 产物可作为有来源的候选输入，不能被展示成 xTB 搜索成功。

### 4.3 正式 TS 优化与验证

`ts_optimization` 只放正式 TS 优化的引擎、方法与优化设置。`verification` 下的 TS 频率、IRC、两侧端点优化与频率各自声明所需计算；两侧端点分别可接收显式替代种子，以支持局部恢复。

现有 `irc_log` 接入能力归入 `verification.irc` 的已有日志来源；核对其 TS 几何、方法、原子身份及实际产物后才可复用，不能因填写路径就认定 IRC 通过。本次不扩展成任意计算结果导入框架。

每份计算声明复用统一的完整方法描述：引擎、方法/基组、显式附加关键词与相应原生任务设置。没有顶层公共方法，没有跨组的隐式复制，没有关键词字符串拼接合并。溶剂、色散等条件由具体完整声明表达并核对。为空的关键词集合与“继承上一步”含义不同。

一开始可显式填全各组，实现完整自动运行；也可先提供部分组，到真正需要缺失输入时停下并列出字段。缺少后续方法不阻止读取或保存路径，不能偷偷补上默认方法。已经提供的方法对象必须结构完整，非法参数直接拒绝。

方法可分别声明不代表任意组合科学兼容。已有同理论级别 Hessian、原子身份、验证证据等约束继续检查；不新增方法选择、通过阈值或评分规则。

### 4.4 编号与引擎切换

内部保持稳定原子身份和 0-based 索引。状态中输出的原子表必须携带结构版本与编号基准，避免跨阶段猜测。

结构类字段沿用独立结构工具的 1-based 约定；原生计算分支的坐标字段沿用 Gaussian 1-based / ORCA 0-based。工具说明逐字段标明所属编号空间，并展示对应表。切换引擎时根据已绑定的内部身份重新渲染，不能把旧数字按新基准再解释一次。输入引用发生变化时重新核验原子绑定。

此规则只明确多引擎分组的边界，不改变各引擎与结构工具既有编号政策。

## 5. resume 的修订语义

`changes` 是统一 input 的局部修订视图，由同一字段定义导出；不手工维护第二份可改字段白名单。

1. 未提供字段保持原值；普通分组内按显式字段修订；列表整项替换，空列表表示清空。
2. 可选输入可用 null 清除；必需的反应身份字段不能清除。清除后仍有科学依赖的，停在缺少输入处。
3. 方法声明、带 kind 的来源和搜索分支按完整对象替换，不合并关键词或不同来源字段。类型和必填项由 Pydantic 校验。
4. 接收修订前检查调用权限、状态版本、在途作业、输入合法性和失败恢复依据。拒绝时不修改已接受声明或作业。
5. 接受后保存前后差异、reason、原失败与恢复证据、失效范围及复用关系，再允许产生新作业。
6. 输入改变不直接指定阶段或成功状态；系统根据已验证证据确定最早需要执行的位置。

语法错误是调用失败。结构合法但科学身份或证据不足，是可查看、可修正的阻塞检查点；即使保存新输入，也不得把相关结果标为合格。

任何关联作业仍在运行或已接受待执行时，本版拒绝流程输入修订，返回具体作业及原因。用户可以查看状态和准备新输入，作业终态后再续接。不新增在途修订队列或自动取消行为。

### 5.1 输入改变后的复用边界

通过现有固定阶段依赖计算失效范围，不新增通用 DAG 工作流引擎。

| 改动 | 保留 | 重新核验/执行 |
|---|---|---|
| 扫描切换为 xTB 路径搜索 | 有效端点、身份及映射；旧扫描历史 | 新路径候选及依赖它的正式链 |
| 更换 TS 初猜 | 有效反应声明与端点资料 | 候选核验、TS 优化及其后续链 |
| 仅改变正式 TS 优化方法或设置 | 仍适用的初猜及上游证据 | TS 优化及依赖其几何/方法的验证 |
| 仅改变某侧端点种子或计算设置 | 适用的 TS、频率、IRC 和独立另一侧证据 | 该侧受影响计算及最终判定 |
| 改变映射、物种、电荷或自旋 | 旧证据作为历史保留 | 所有依赖这些输入的身份、计算与判定 |
| 只改变资源申请 | 已完成且有效的科学产物 | 后续新作业按新资源申请；失败重试仍需恢复依据 |

“失效”表示不能再支撑当前修订的结论，不删除原文件或作业。复用必须核对结构版本、原子身份、方法与相关参数，不能只按阶段名或文件是否存在判断。

### 5.2 失败恢复与同一输入的重试

`recovery` 包含 `failed_attempt` 与 `evidence_refs`，仅在处理已有失败时提供，绑定实际失败尝试和可检查的恢复证据；reason 说明改动如何处理该失败。它可与 changes 一同提交，也可在输入未变但执行环境已修复时单独提交。更换几何、扫描或方法仍通过 changes 表达，无需另设 retry_action 枚举。

相同失败输入、相同执行条件不能反复提交。软件/文件环境已修复时，证据绑定实际恢复条件，形成可追溯的新尝试；“再试一次”或新的请求键不构成修复。

已知机械失败可按原生错误分类及可检查产物核对。科学修复是否充分不能用关键字或自由文本评分猜测；无法确认时保留可解释的决策检查点，由获准科学判断补足依据。

## 6. 状态、读取与自动推进

采用一个公共状态投影供 prepare、resume、inspect 和通知复用，默认返回紧凑摘要：

| 字段 | 含义 |
|---|---|
| `run_id`, `revision`, `run_dir` | 路径身份、当前权威快照版本、文件入口 |
| `status`, `stage` | 当前在推进、等待、阻塞或本次尝试结束；具体计算子步骤可辨认 |
| `result` | 本次尝试的科学结论及证据引用；正在重算时不能继续展示旧结论为当前结论 |
| `waiting_for` | 真实作业编号、用途和调度状态 |
| `available_results` | 当前仍有效的结构和计算证据及来源 |
| `blocked` | 原因、原生日志摘要/引用、具体缺失条件 |
| `next` | 当前可继续的操作、可修改字段组与所缺输入；由状态及调用者权限计算 |
| `methods` | 各阶段实际采用/计划采用的方法与任务约定核对情况 |
| `usage` | 实际耗时、已分配资源及可获得的实际消耗；未知值明确缺失 |
| `details_path` | 完整有效输入、阶段记录、历史尝试和变更影响的可读导出 |

resume 另外返回本次修订回执：差异、保留/失效结果及接下来执行的步骤。该回执也持久化供 inspect 的详细记录访问；不增加每一步人工确认。

inspect 读取 compute 数据库权威记录，结合已记录作业状态生成快照；不能推进 driver、修复状态或触发昂贵重新解析。详细导出由写入/推进路径维护，读取不写检查点。若导出暂时滞后，明确给出其版本，不能把它当作最新事实。

调用是否成功与科学是否成功分别表达。阻塞可以是成功处理的调用；`verified` 才是对应证据链通过，不能用工具成功字段代替。

`verified / candidate_only / search_failed / invalid_input` 继续作为某次尝试的结果。它们不永久封死路径：有合法新输入可在原 run 建立新修订和尝试，包括已验证后继续探索；原结论保存在原尝试上。无改变的调用不能自动重复已结束的链条。resume 开始新尝试后，当前结果按新修订重新判定。

正常完成事件交给现有 `ts_pipeline_driver`，自动提交下一个已具备条件的步骤。只在需要决策或本次尝试结束时通知 Agent；中间进度可通过 inspect 读取。重复事件、重启 reconcile、请求重放均不能重复入队。

## 7. 删除时间预估

- 从 TS 的公开输入、持久化的当前声明、准入路径与提示中删除 `compute_estimates` 及 `estimated_cpu_hours` 上限。
- 覆盖扫描、路径、构象优化及逐点梯度/Hessian 等 TS 子作业，不能在内部适配器中残留“估计缺失则拒绝”的条件。
- 不把缺失预估转成零成本，也不自动生成一个估计填进去。
- 保留作业真实起止时间、运行时长、资源分配及已有可测消耗。“核数 × 占用时长”如有展示，明确是分配量，不冒充测得的 CPU 使用。
- 已配置的计算动作数、模型调用数额度继续复用既有机制，集中到 execution 的对应语义中，不增加新的额度类型。2026-10-18 用户要求移除所有 TS 任务的介入次数上限，覆盖此前保留该额度的决定。
- 不修改共享预算设施中与 TS 无关的调用者行为；必要时收窄 TS 适配层。历史预估记录可以归档，但不能继续影响新的 TS 准入。

## 8. 四个 issue 的处理范围与关闭条件

### #108：只读复核任务仍可提交计算

链接：https://github.com/yyywaa/Cloudra-mechanism-agent/issues/108

**可以同批解决，但需要跨出 TS 模块。** TS 层提供 inspect 的只读访问，并在写入口和内部计算提交核验生产权限。复核分工通过现有只读角色和运行权限表达，不能靠解析“只读复核”这段自然语言。

权限来源为可信任务/运行上下文，工具参数和 reason 不能自授权限。复用现有角色与委派链进行能力收窄：只读职责不能通过普通计算提交、TS、脚本、AgentHub 或创建执行者取得生产权限。创建/调用其他 Agent 的检查必须覆盖实际公共委派入口，不能只看 can_spawn。

inspect 的读权限按项目与既有证据访问范围判断，不要求是原 owner。写权限沿既有生产归属和任务授权判断；本次不新造任意所有者转移 API。系统自动续接携带原生产任务的有效授权，不以“系统内部调用”为由绕过检查。权限不再允许新增作业时，阻止下一次入队并保留既有作业运行。

关闭条件：只读复核者能读同项目获准证据，普通提交、TS 写操作、脚本及委派绕过均在入队前被拒绝；获准生产者的自动链通过；跨项目拒绝；现有 QM 保活。只完成 inspect 或 TS 入口检查不能关闭该 issue。

### #109：元素一致映射掩盖输入身份问题

链接：https://github.com/yyywaa/Cloudra-mechanism-agent/issues/109

**纳入输入来源接入与前置核验。** 使用现有具体结构身份、立体和映射检查，在路径搜索及正式 QM 前核验实际输入；结果绑定结构内容及声明版本。明确 mismatch 阻塞；inconclusive 返回缺少的证据和有歧义的绑定，不能被后来填入的元素置换抹去。

核验针对实际要使用的准备后几何；预组织、种子替换或其他几何变更可能使旧核验失效。对称原子的多个合法映射不能自动等同于物种错误，也不能自行任取一个宣布绑定完成；沿用已有科学证据表达，不新增阈值。

关闭条件：元素一致但物种错误的输入不进入后续昂贵计算；歧义可解释；已证明身份与映射的输入正常推进；替换结构后重新检查；最终仍核验实际 TS/IRC/端点产物。

### #110：失败扫描仅改点数即可重新提交

链接：https://github.com/yyywaa/Cloudra-mechanism-agent/issues/110

**纳入 resume 接受条件与尝试历史。** 持久保存原失败类别、原生日志引用/摘要、有效扫描输入和本次差异。第一点优化或临时输入读取失败后，仅改变总点数不视为修复；相同失败输入及条件不重交。

有根据的扫描细化、换起点、换搜索路线继续允许，但每次恢复要关联原失败并说明实际改变。恢复证据由显式 artifact 引用提供；reason 单独存在不等于修复成立，不扩大任务额度。基础设施修复使用第 5.2 节的 recovery 语义。

关闭条件：7 点改 8 点的原始反例不重交且保留阻塞；完全相同输入不重交；有匹配恢复证据及授权的调整能继续；重启后规则仍有效；正常自动下一阶段不受影响。

### #111：扫描与正式方法混填、漏填或未经授权改变

链接：https://github.com/yyywaa/Cloudra-mechanism-agent/issues/111

**纳入方法分组和实际输入核对。** 每次提交前从最终生成的原生输入提取有效方法、基组、附加条件、溶剂、电荷和自旋，与该阶段显式声明及任务已确认约定核对。展示具体缺项/差异；已有规范化规则认可的等价写法不误拒。无法可靠解析时明确阻塞，不通过正则猜测结构化入参。

扫描与 TS 优化方法不要求相同。本次用户允许 Agent 显式选择扫描半经验方法，这属于获准探索差异；其能量不能替代正式精修证据。若任务另有完整扫描方法约定，则按该约定检查。正式方法的变化仍受任务科学授权约束，不能仅凭 Agent 把新方法填进 changes 就证明已获准。

可信方法约定来自用户/任务的已确认上下文；Agent 修改后的声明不能同时充当授权来源。实现须保留这一来源绑定；缺少可核对约定时如实显示缺失，并对需要科学授权的变化请求补足，不能捏造批准。

关闭条件：缺少已要求的 D3BJ 等条件会在入队前发现；未授权换正式泛函/溶剂/电荷/自旋返回差异；获准扫描路线可运行；扫描、TS、Freq、IRC、端点均可追溯到实际方法和声明。

## 9. 持久化、运行安全与实现边界

沿用 compute.db 的流程、声明修订、阶段尝试和作业绑定，process.json 作为可读导出。修订、失效关系与新作业绑定须保证事务一致性，写入完成后再执行副作用。

原生输入和已绑定产物不可原地覆盖。用现有哈希与版本检查证据，进程保活仍以 flock 为准。修订、拒绝、失效和权限错误均不能杀 QM，也不能把持锁作业标成失败。

本次不考虑旧接口兼容：删除被替代的平铺参数、旧空 resume 读语义、失效提示和重复实现。持久记录采用显式格式版本；旧格式的已有计算必须继续受调度器/Guard 保护，其原始记录保留。新 driver 对不支持的旧格式明确隔离自动推进，不崩溃拖垮其他流程，不重新解释后重交，也不结束已在运行的计算。上线前确认在途旧流程的处置，不能用“无兼容”作为丢弃作业的理由。

实现集中在现有模块：

| 模块 | 职责调整 |
|---|---|
| `tools/Chemtool/ts_search_process.py`、工具注册/能力投影 | 分组输入、对称续接、只读 inspect、清楚的工具说明 |
| `tools/core/ts_process.py` 及现有准备/扫描/候选适配器 | 前置核验、输入修订、阶段依赖失效与复用 |
| `services/ts_pipeline_store.py`、现有数据库模型 | 权威状态、请求幂等、尝试与修订回执 |
| `tools/core/ts_pipeline_driver.py`、`runtime_v2/compute_notify.py` | 自动接续、恢复和通知；清理旧 resume 指引 |
| 已有计算准入、权限、角色与委派入口 | #108 的一致执行与 #111 的方法核对 |
| 现有预算适配及调用点 | 删除 TS 时间预估依赖，保留实际记账 |

所有阻塞 I/O 从异步事件循环卸载。校验只用 Pydantic、结构化解析或明确 token/枚举；正则只允许用于原始 QM 日志解析。

## 10. 验收与验证

规格不等于实现完成，四个 issue 也不因本文产生而关闭。实现需要至少覆盖以下可重现行为：

1. 一次 prepare 正常跑完整链，零人工 resume；重复通知不重交。
2. 同一 run 经扫描失败、换路线、换初猜和局部端点恢复继续，保留失败及有效证据。
3. prepare 可表达的科学输入均可在 resume 修订，字段没有第二份失配白名单；不允许输入直接写入成功状态。
4. 不同方法组隔离；未声明方法时明确缺失；切换 guess kind 清除旧分支参数；方法完整替换。
5. inspect 在等待、阻塞、完成与重启后均可用；调用前后数据库修订、作业数、介入数不变；只读角色可访问获准内容。
6. 旧 revision、跨项目、重复键冲突、运行中修订均明确拒绝且无额外作业；重复已处理请求返回原处理回执。
7. TS 任何子阶段不再依赖估计时间准入；实际耗时仍有记录，未知消耗不记成零。
8. 各 issue 第 8 节的关闭条件都有针对性回归测试；#108 验证完整生产入口，不能只 mock TS 工具。
9. 锁定作业在失败、拒绝、权限变化和恢复路径中保持运行；不得误标 failed。
10. 不支持的旧记录格式不影响其他流程恢复，也不改变已有 QM 作业。

本地执行语法检查、ruff，再运行受影响模块测试；不运行全套 tests。状态机交互回归使用 ScriptedProvider，检查事件、状态、持久化及入队次数，不断言模型自然语言。

接口与恢复测试优先使用 fixture；涉及原生输入/解析变化时增加对应引擎产物回归。真实引擎验收与单元测试结论分别记录，不把单测通过宣称为科学流水线已实跑通过。

实现完成后同步 `docs/TS_PROCESS_SOP.md`、工具说明及相关科学技能指引，删除“不设查询接口”“完成后手动 resume”等冲突说明。四个 issue 按各自验收证据单独判断是否关闭。
